# Auth Endpoints

The Orchid API exposes authentication endpoints for OAuth flows, identity resolution, token management, and session warming. These endpoints enable the frontend and MCP gateway to authenticate users and obtain tokens without direct access to authentication secrets.

## /auth/info

Returns non-secret OAuth discovery information. Used by frontends and MCP hosts to discover the auth configuration:

```
GET /auth/info
```

Response:

```json
{
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "registration_endpoint": "https://auth.example.com/register",
  "issuer": "https://auth.example.com",
  "scopes_supported": ["openid", "profile", "email", "offline_access"],
  "response_types_supported": ["code"],
  "code_challenge_methods_supported": ["S256"],
  "refresh_via_api": true
}
```

The response is generated by `OrchidAuthConfigProvider`, a pure config-resolution ABC with no network calls. The `refresh_via_api` flag is `true` when `OrchidAuthExchangeClient.refresh_token` is overridden (not the default `NotImplementedError`).

## /auth/exchange-code

Exchanges an authorization code for tokens. Used after a user completes the OAuth authorization flow:

```
POST /auth/exchange-code
Content-Type: application/json

{
  "code": "authorization-code-from-upstream",
  "code_verifier": "pkce-code-verifier-from-client",
  "redirect_uri": "http://localhost:3000/callback"
}
```

Response (200):

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "refresh_token": "rt_secret_refresh_token...",
  "expires_in": 3600,
  "token_type": "Bearer",
  "scope": "openid profile email"
}
```

Error (400):

```json
{
  "error": "invalid_grant",
  "error_description": "The authorization code is invalid or expired"
}
```

### Security Checks

The endpoint validates:
- The authorization code is valid and not expired.
- The `code_verifier` matches the `code_challenge` used in the authorization request (PKCE).
- The `redirect_uri` matches the one used in the authorization request.

## /auth/token

Refreshes an expired access token using a refresh token:

```
POST /auth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=rt_secret_refresh_token...
```

Response (200):

```json
{
  "access_token": "eyJhbGciOiJS...",
  "refresh_token": "rt_new_refresh_token...",
  "expires_in": 3600,
  "token_type": "Bearer"
}
```

Token rotation: a new refresh token is issued with each refresh. The old refresh token is invalidated.

## /auth/resolve-identity

Bridges an upstream token to an Orchid identity. The core identity resolution endpoint:

```
POST /auth/resolve-identity
Authorization: Bearer <upstream-token>
```

Response (200):

```json
{
  "user_id": "user-123",
  "tenant_key": "my-tenant",
  "access_token": "orchid-bearer-token-for-downstream",
  "metadata": {
    "email": "user@example.com",
    "name": "Jane Smith"
  }
}
```

### How It Works

1. Client sends an upstream bearer token to `/auth/resolve-identity`.
2. The API calls `OrchidIdentityResolver.resolve(domain, bearer_token)`.
3. The resolver validates the upstream token (JWT signature, expiry, audience).
4. Returns an `OrchidAuthContext` that the API serializes.
5. The client receives an Orchid identity it can use for subsequent API calls.

### Use Cases

- **MCP Gateway** — Bridges MCP host identity to Orchid identity.
- **Frontend** — After NextAuth login, resolves the OIDC token to an Orchid identity.
- **Service-to-service** — Bridges a service's token to an Orchid identity for API calls.

## /session/warm

Warms MCP capabilities for the current user session:

```
POST /session/warm
Authorization: Bearer <orchid-token>
```

Response (200):

```json
{
  "status": "warmed",
  "servers_warmed": 3,
  "tools_discovered": 12,
  "duration_ms": 450
}
```

### What It Does

1. Calls `OrchidSessionWarmer.warm_user(auth)` for the authenticated user.
2. Discovers tools from all `passthrough` and `oauth` MCP servers.
3. Caches capabilities for the session lifetime.
4. Ensures the first agentic turn has no discovery delay.

The frontend calls this endpoint on session start. A fire-and-forget backstop in `get_auth_context()` ensures warming happens even if the frontend doesn't call it.

## Implementation

All auth endpoints delegate to ABCs in `orchid_ai/core/`:

- `/auth/info` → `OrchidAuthConfigProvider` (pure config, no network).
- `/auth/exchange-code` → `OrchidAuthExchangeClient.exchange_code()`.
- `/auth/token` → `OrchidAuthExchangeClient.refresh_token()` (if overridden).
- `/auth/resolve-identity` → `OrchidIdentityResolver.resolve()`.
- `/session/warm` → `OrchidSessionWarmer.warm_user()`.

Concrete implementations are injected from consumer projects via dotted import paths in `orchid.yml`.
